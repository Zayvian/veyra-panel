# 面板 ↔ 节点控制协议

节点主动连接面板的 `wss://<面板>/api/v1/node/connect`，用 `Authorization: Bearer <join token>` 认证。之后双方在这条 WebSocket 上互发 JSON 文本帧。节点不需要开放任何控制端口。

两边各自定义了一份消息结构体：面板在 `panel/internal/hub/proto.go`，节点在 `node/internal/proto/proto.go`。两边**故意不共用 Go 包**：面板和节点的许可证不同，它们之间的约定只有线上的 JSON 格式。保证两边一致的是 `testdata/` 里的样例。

## 信封

每一帧都是一个信封：

| 字段 | 类型 | 说明 |
|---|---|---|
| `t` | string | 消息类型，见下表 |
| `id` | uint64，可省略 | 命令和回复用它对应；单向上报时省略 |
| `d` | object，可省略 | 消息内容，结构由 `t` 决定 |

## 消息

| `t` | 方向 | `d` 的结构 | 说明 |
|---|---|---|---|
| `hello` | 节点 → 面板 | `version` `os` `arch` `hostname` `singbox_version`；`proto` `caps`（协议 2 起） | 连接后第一条消息。面板收到后立即下发 `config` 和 `users` |
| `welcome` | 面板 → 节点 | `proto` `caps` | 协议 2：只回给 `hello` 里 `proto ≥ 2` 的节点，并且**在 `config` 之前**发送 |
| `config` | 面板 → 节点 | `config`：完整的 sing-box 配置，入站里不带用户；`rev`：配置的 SHA-256 | 节点重建 sing-box 实例。配置和上次完全相同时节点不重建 |
| `users` | 面板 → 节点 | `by_tag`：入站 tag → 用户列表；`stats_users`：统计白名单；`ip_limits`：用户名 → 同时在线 IP 上限（可省略） | 全量替换，不是增量。节点热替换用户，不断开其他连接 |
| `ok` | 双向 | 无 | 节点 → 面板：某个 `id` 的命令执行成功。面板 → 节点（`stats_ack`）：编号为 `id` 的流量报告已经入账 |
| `error` | 节点 → 面板 | `msg` | 对某个 `id` 的命令执行失败，节点继续运行旧配置 |
| `state` | 节点 → 面板 | `inbounds`：实际在运行的入站 tag；`error`（可省略）；`applied_rev`（`config_rev`） | 每次尝试应用配置后发送，说明节点实际在跑什么 |
| `stats` | 节点 → 面板 | `users`：用户名 → `{up, down}`；`system`（可省略）；`epoch`（`stats_ack`） | 距上次上报的**增量**字节数，不是累计值。`stats_ack` 下信封 `id` 是报告编号 |
| `online` | 节点 → 面板 | `users`；`ips`（可省略）；`activity`（可省略） | 当前在线用户、各自的来源 IP 数和连接形态（只有计数，不含目标地址） |
| `panel_url` | 面板 → 节点 | `url`：面板的新地址 | 协议 2，`panel_url` 能力：面板换了域名，节点以后改连这个地址。见下文 |
| `ping` | 面板 → 节点 | 无 | 保活 |
| `pong` | 节点 → 面板 | 无 | 回应 `ping`，`id` 相同 |

用户条目的字段：`name`，以及按协议使用的 `uuid`、`flow`（VLESS）或 `password`（AnyTLS、Shadowsocks 等）。

## 协议 2：能力协商

节点在 `hello` 里写 `proto: 2` 和自己支持的 `caps`。面板如果也支持协议 2，就先回一条 `welcome`，写明面板支持的 `caps`，然后才发 `config`。**某项能力只有双方都列出来时才启用。**

- 旧节点不发 `proto`，面板就不发 `welcome`，一切照旧。
- 旧面板不认识 `proto`，直接发 `config`。节点没先收到 `welcome`，就按旧方式工作。
- 每次重连都重新协商：中间面板可能升级或回退过。

### `stats_ack`：流量报告确认

旧方式下，节点把报告写进连接就当作完成。如果连接在面板入账前断了，这段流量就丢了。

`stats_ack` 下：

1. 节点每个进程有一个随机的 `epoch`，每份报告有递增的编号（放在信封 `id` 里）。
2. 面板入账之后回 `ok`，`id` 和报告编号相同。**节点收到这个 `ok` 才算报告完成。**
3. 没收到 `ok` 之前，节点每次都**原样重发同一份报告**（同一个 `epoch`、编号和流量），也不读取新的流量。重连之后同样重发。
4. 面板在 `nodes` 表里记着每台节点最后入账的 `(epoch, 编号)`，和流量写在同一个事务里。收到同一个 `epoch` 下编号不大于它的报告，就是重复的：**不再入账，但照样回 `ok`**，否则节点会一直重发。
5. 新的 `epoch` 表示节点进程重启过，编号从 1 重新开始。

这样报告既不会因为断线丢失，也不会因为重发被重复计费。唯一的例外：面板恰好在一份报告入账后、`ok` 送达前回退成旧版本，旧面板认不出重发，这一份会被记两次。

### `config_rev`：配置版本

面板发的每份 `config` 都带 `rev`（配置 JSON 的 SHA-256）。节点应用成功后，在 `state` 的 `applied_rev` 里回报正在运行的 `rev`；应用失败时仍回报上一份的 `rev`。面板对比 `applied_rev` 和当前应有的 `rev`，就能区分「已生效」「等待节点应用」和「节点拒绝」。只看入站 tag 是做不到这一点的：改端口、改证书不会改 tag。

### `panel_url`：面板换域名

管理员在面板「设置」里更换域名后，旧域名会继续保留一段时间，节点仍然能连上。节点连进来时，面板看它连的是哪个域名（请求的 Host）。如果不是面板现在的域名，并且双方都支持 `panel_url`，面板就发一条 `panel_url`，`url` 是 `https://<新域名>`。

节点收到后：

1. 先检查新地址：只接受 `https://`，并且 `GET <url>/api/v1/node/connect`（不带令牌）必须通过 TLS 证书校验、返回 401。这说明新域名已经解析到面板、证书已经签好。
2. 检查不通过：回 `error`，继续用旧地址。下次重连时面板会再发。
3. 检查通过：把新地址写进节点的环境文件（`SKYSBX_PANEL=`，默认是工作目录下的 `node.env`），回 `ok`，然后断开当前连接，用新地址重连。以后升级节点、重启节点，用的都是新地址。

## 修改协议的规矩

1. **先改 `testdata/` 里的样例**，再改两边的结构体。
2. 面板的 `panel/internal/hub` 和节点的 `node/internal/proto` 各有一个测试：把每份样例解析成自己的结构体，再编码回 JSON，结果必须和样例完全一致。字段改名、漏字段、`omitempty` 写错，都会让其中一边的测试失败。
3. 两边测试都通过之后才能合并。
4. 新字段要能被旧版本忽略：旧节点不认识的字段会被丢弃，旧面板同理。需要双方都支持才能启用的功能，要先在 `hello` 里协商。
